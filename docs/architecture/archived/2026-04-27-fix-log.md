# Fix Log — 2026-04-27 Night Session

Running ledger of every behavioral change shipped tonight, what bug it
fixed, and why we believed the change was the right one. Append-only.

## Bugs (silent failures that lost real money)

### 1. Drift block silently dropped 998 rescue intents per hour
- **Commit**: `e337be4` then refactored in `b7aff28`
- **Symptom**: 998 hedge rescue intents BUILT inside strategy per hour,
  ZERO ever appeared at venue. Stranded inventory accumulated forever.
- **Root cause**: `accept_intent` drift block (`runtime/mod.rs:1826`)
  rejected ALL `!reduce_only` intents on drifted markets. Rescue intents
  are `reduce_only=false` (BUYs to manufacture missing leg) but they're
  CLOSE-side operations, not fresh entries. Every supervisor restart
  re-engaged the drift block on every market we held inventory in, then
  trapped every subsequent rescue.
- **Fix**: Added rescue bypass. Then refactored as `IntentKind::{Entry, Close}`
  enum so any FUTURE gate auto-bypasses without remembering string check.
- **Why this fix**: 5 separate `quote_level_tag.starts_with("mm-hedge-rescue")`
  checks already existed across runtime, risk, reconciler, runner. The
  drift block was the 5th. Per CLAUDE.md "Distinguishing entry vs close
  intents" — promote to typed enum at threshold of 4+ duplicate checks.

### 2. `pending_merge_by_market` never cleared on submit failure
- **Commit**: `ecb327c`
- **Symptom**: When a merge failed (transient RPC error), the runner logged
  "will retry on next reconcile sweep" — but the dedup key stayed.
  Future merge attempts on same market silently skipped.
- **Root cause**: `pending_merge_by_market` HashMap entry was inserted
  at submit time (`mod.rs:772`), only cleared on successful FILL arrival
  (`mod.rs:1216`). All 3 failure paths in `runner.rs:2778-2810` left
  the entry orphaned.
- **Fix**: Added `Runtime::clear_pending_merge()`, called from all 3
  failure paths.
- **Why this fix**: Symmetric with how successful fills clear the entry.
  No new state machine; just complete the existing one.

### 3. Asymmetric (true, true) inventory had no rescue path
- **Commit**: `1ccef91`
- **Symptom**: Market `btc-updown-5m-1777282500` bled -$20.55 in 30min.
  We bought 52 Up shares (sellers dumping in trending tape) but only 5
  Down. Strategy treated (true, true) as "no-op = balanced" while 47
  shares of stranded Up rode to resolution against the trend.
- **Root cause**: `(true, true) => {}` no-op branch at `strategy.rs:2355`.
  The merge engine pairs MIN(left, right); excess is unpaired and bleeds
  at resolution if favored side loses.
- **Fix**: Added asymmetric rescue branch — if `abs(left-right) >= venue_min`,
  fire rescue for the under-stocked leg.
- **Why this fix**: Same shape as the symmetric (true, false) rescue
  path. The "balanced" semantic was wrong — equal qty is balanced, not
  any nonzero qty.

### 4. FAK rescue limit price was stale (ate 100s of FAKs)
- **Commit**: `4727951`
- **Symptom**: Polymarket returning `"no orders found to match with FAK
  order. FAK orders are partially filled or killed if no match is found."`
  on rescue submits. Hundreds of rescues failing per hour.
- **Root cause**: depth-walk computed sweep_price from local book
  snapshot. By the time the FAK reached the venue (50-200ms later), best
  ask had ticked up. FAK with no match → killed.
- **Fix**: Added `hedge_rescue_race_buffer_ticks=3` — pad the rescue
  limit upward by 3 ticks. Capped at $0.99 to maintain net-positive.
- **Why this fix**: 3¢ extra per share vs $0.50+ rescue gain = trivial
  cost; eliminating the kills was a step-change.

### 5. Sub-min stranded inventory couldn't be rescued
- **Commit**: `61c9903`
- **Symptom**: Stranded qty=4.99 (sub-venue-min) → rescue intent build
  returned None silently.
- **Root cause**: `build_rescue_intent_for_quantity` had check
  `sweep_qty < venue_min_order_quantity → None`. Rescue qty is dictated
  by stranded inventory; venue requires ≥5 shares; you can't have <5
  stranded ever rescued. Forever stuck.
- **Fix**: Upsize `sweep_qty` to venue minimum. The merge engine pairs
  MIN(left, right) so the (venue_min - stranded) residual becomes a
  tiny new stranded position bounded by venue_min.
- **Why this fix**: Same principle as other 4 cap-bypass layers — close
  intents must not be trapped in caps designed to prevent the exposure
  they're trying to unwind.

### 6. Paired bids hit venue's "post-only crosses book" race
- **Commit**: `a0aa4e4` (later refined in `df92f76`)
- **Symptom**: 31 paired-bid rejections per 6h, error: `"invalid post-only
  order: order crosses book"`. Same race pattern as #4 but for paired
  entries.
- **Root cause**: With `safety_ticks=1`, our buy was 1 tick below ask.
  Book ticks down → our buy = new ask → crosses → post-only kills.
- **Fix**: Bumped `maker_safety_ticks` 1→3, then back to 2 (3 cratered
  fill rate too far). Also threaded venue tick from MarketMetadata.
- **Why this fix**: Mid-ground between fill rate and rejection rate.

## Tunings (not bugs, just calibration)

### 7. Regime gate threshold 5.0 → 0.3 → 0.1 bps
- **Commits**: `1da094e`, `422f1ee`
- **Why**: 5.0 was set assuming sparse BTC sampling; with dense (~10/sec)
  per-tick returns are tiny (sub-bp). Gating 92% of attempts left the
  bot mostly idle. Lowered to 0.1 — only skip truly-dead tape.

### 8. Spot momentum tilt on fair_value
- **Commit**: `bb6f418`
- **Why**: fair_value was pure book mid → no directional adjustment as
  BTC moved → adversely selected on every directional tick. Added small
  bias `momentum_tilt_per_bps * return_60s_bps` on UP leg. UP/DOWN
  identity from `MarketContextRecord.instrument_ids[0]` (Polymarket gamma
  convention).

### 9. Fill-rate-aware clip sizing
- **Commit**: `ad05ee2`
- **Why**: Mirror unlawful's compounding pattern. When fills come in,
  scale clip up (1.0x → 2.0x with 10 fills/5min). Asymmetric: never
  scales down (regime gate handles dead tape; shrinking below venue min
  makes orders unfittable).

### 10. include-prev/next 0 → 1 (3 markets concurrent)
- **Commit**: `df92f76`
- **Why**: Engine already handles multi-market; supervisor was cycling
  through them anyway via restarts. Mirrors unlawful's verified
  3-bar-window subscription pattern. Low cost, ~50-80% throughput gain.

## Architectural improvements

### 11. Venue MarketMetadata threading
- **Commit**: `35be520`
- **Why**: We had `venue_min_order_quantity` and `maker_price_tick` as
  Btc5mMmConfig env knobs. These are venue facts, not strategy choices.
  Operators kept env in sync with what Polymarket required. Now strategy
  reads them from `Runtime::venue_market_rules` cached on first reconcile.
  The config defaults remain only as fallback for first-tick before
  cache populates.

### 12. IntentKind type promotion
- **Commit**: `b7aff28`
- **Why**: 5 separate string-prefix checks for "is rescue" across the
  codebase. Each new gate someone adds risks forgetting the bypass.
  Promoted to `OrderIntent.kind: IntentKind { Entry, Close }`. One
  source of truth.

### 13. Maker rebate program discovered
- **Doc**: `project_2026-04-27_maker_rebates_real.md`
- **Why**: I'd previously concluded 5min crypto markets had no rebate
  program (looked at the wrong endpoint — `clobRewards`/`/orders-scoring`
  is the OLD Q-score program). The NEW dynamic-taker-fee program pays
  20% of taker fees daily as USDC airdrop to maker_address. Endpoint:
  `clob.polymarket.com/rebates/current?maker_address=...&date=YYYY-MM-DD`.
  Our wallet earned $5.90 across 87 markets on 2026-04-26 alone.

## Observations from live trade analysis (during session)

### Observation 1: $0.93 Down fill bleed
- **Timestamp**: ~10:00 UTC, 2026-04-27
- **Pattern**: Cash dropped $98 → $67 in ~30min. Bot held 12.77 Down shares
  at avg cost \$0.93. Market reverted to 50/50.
- **Root cause**: Strategy posts at fair_value = book mid. When book momentarily
  showed Down=\$0.93, fair_value computed Down at 0.93, paired bid posted at
  \$0.92, taker hit, we filled. Then book reverted.
- **Fix**: Price-extremity gate (commit `0c5fbad`) — skip entry when
  `max(left_fair, right_fair) > 0.85`. Mean-reversion EV is negative
  above this threshold.

### Observation 2: post-merge re-entry on trending market
- **Market**: btc-updown-5m-1777283700, ~10:02 UTC
- **Pattern**: 1) Bought 15 Up at \$0.48; 2) asymmetric-rescued via 16.9
  Down at \$0.15; 3) merged 15 paired (\$15 release); 4) **immediately
  re-entered**, bought 7 more Up at \$0.36-\$0.42; 5) re-stranded, ~\$16 loss.
- **Root cause**: Strategy is stateless per-market between snapshot ticks.
  After successful merge, inventory = (0,0), regime gate passes, extremity
  gate passes (max_fair=0.62). Strategy re-enters as if fresh market.
- **Fix**: Post-fill per-market entry cooldown (commit `b59972d`).
  Wait 30 × cooldown_ms (~15s) before re-entering same market after a fill.

### Observation 3: rescue correctly REFUSES bad rescues
- **Market**: btc-updown-5m-1777284000 with 37.6 Up + 1.9 Down stranded
- **Pattern**: Asymmetric rescue branch entered 187 times, `intent_built=false`
  every time. Down ask was at \$0.98 (Up had crashed to \$0.02).
- **Why correct**: Rescue economics: buy 35 Down at \$0.98 = \$34.30, merge
  35 paired = \$35.70 release, but already-spent \$14.43 on Up is sunk →
  net -\$13. Strategy refuses to compound the loss.
- **Real fix needed**: per-market trend detection at ENTRY time. When a
  market's mid is moving rapidly (not just BTC vol), pause entry to avoid
  this trap. Currently regime gate only checks BTC spot, not market-level
  trend. (TODO)

### Observation 4: data-api activity feed lacks `isMaker` field
- The `https://data-api.polymarket.com/activity` endpoint does NOT return
  `isMaker` — earlier analysis claiming 100% taker was wrong (Python
  `.get('isMaker')` returned None = falsy).
- **Maker/taker detection proxy**: round-cent price = MAKER (we were
  resting at exact tick). Sub-cent decimal price = TAKER (venue computed
  fill price for FAK sweep).
- **Verified**: 99.8% of our fills are MAKER (round-cent). Same as
  unlawful (100% MAKER). Quality ratio is good; throughput is the gap.

### Observation 5: maker rebates use a SECOND endpoint (commonly missed)
- `clobRewards` field + `/orders-scoring` endpoint = OLD Q-score program,
  not funded on 5min crypto.
- `/rebates/current?maker_address=...&date=...` = NEW dynamic-taker-fee
  program, IS funded on 5min crypto. Pays 20% of taker fees daily as
  USDC airdrop. Our wallet earned \$5.90 across 87 markets on 2026-04-26.
