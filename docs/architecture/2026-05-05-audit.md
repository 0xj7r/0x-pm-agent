# Engine Audit — 2026-05-05

Scope: redundancy, overlap, and bug surface in the Rust execution engine, with focus on the **paired MM + late-convex accumulation** primary strategy and the recurring **stranded inventory** incident class.

This document is analysis only. Each finding has file:line citations and a concrete recommendation. Nothing here changes code. Findings are ranked by likely impact on stranded-inventory.

---

## Finding 1 — Convex package legs lack `pair_id` atomicity

**Severity:** High. Direct stranded-inventory surface.

`paired_mm/engine.rs:556` and `paired_mm/engine.rs:588` build the favorite-leg and tail-leg `OrderIntent`s for the late asymmetric convex package. Neither sets `pair_id`. They go to the runtime as two independent intents.

The runtime's atomicity guard (`runtime/mod.rs:2601` `filter_incomplete_paired_entry_intents`, `runtime/mod.rs:1991-2033` post-rejection mate cancellation) only fires for intents where `pair_id` is set AND `is_paired_entry_intent` returns true. `is_paired_entry_intent` (`runtime/mod.rs:2655`) checks for `quote_level_tag` containing `mm-paired-bid` or `:PairedEntry`. **The convex overlay tags use `mm-convex-accum:`**, so the convex package is invisible to the atomicity guard.

Consequence: if the favorite leg fills and the tail leg does not (price walks, partial venue match, leg-level cancel), the favorite is stranded. The rescue path will eventually detect this via `derive_tick_rescue_inputs` (`paired_mm/engine.rs:329`), but only after `min_imbalance_qty` is exceeded, and meanwhile the convex overlay loop may re-arm the favorite leg again as soon as `favorite_open_count` drops to zero (line 469).

**Recommendation:**

1. Set `pair_id = Some(format!("convex-package:{market_id}:{now_ms}"))` on both intents in the package branch.
2. Update `is_paired_entry_intent` to branch on `IntentKind` and any "this is part of a multi-leg group" flag, not on the `quote_level_tag` substring. A clean way is to add a `pair_atomicity: bool` field on `OrderIntent` (or, cleaner still, derive it from `pair_id.is_some()` since pair_id only exists for atomicity-required groups today).
3. The favorite-only branch (`engine.rs:640-668`) is correctly unpaired — leave it.

## Finding 2 — Two parallel inventory accountings, both authoritative

**Severity:** High. Silent divergence directly causes stranded-inventory non-detection.

The engine maintains inventory in two places that are both updated from fills but live in different modules and are not reconciled against each other:

| Store | Lives in | Updated from | Used by |
|---|---|---|---|
| `InventoryState` (`core/inventory.rs:1` onward) | `Runtime.inventory` | `Runtime::on_fill` and reservation/release | risk caps, merge gate, dashboard, drift detection |
| `AutoFillState` (`paired_mm/fill_automation.rs:73`) | `PairedMmEngine.fill_state` | `PairedMmEngine::on_fill` (`engine.rs:169`) | the post-fill rescue trigger |

Both are derived from the same fills, but the rescue trigger runs against `AutoFillState` only. If the runtime restarts and replays fills only into `InventoryState` (via durable order/position state), the `AutoFillState` lots are reset to whatever is in the `from_snapshot` payload. If snapshotting drifts from the runtime's view, the rescue brain has a different idea of what is stranded than the merge brain does.

There is also a third "view": `derive_tick_rescue_inputs` at `engine.rs:329` reads `PairedInventorySnapshot.yes_qty / no_qty` (which is built from the runtime's authoritative inventory at the call site). So the engine has **two rescue triggers**: one fed by the runtime's view (engine.decide → derive_tick_rescue_inputs), one fed by the paired-MM-local view (engine.on_fill → AutoFillState).

**Recommendation:**

1. Treat `InventoryState` as the single source of truth.
2. Either:
   - Make `AutoFillState` a derived view of `InventoryState` (e.g. it keeps the cooldown timestamps but reads positions from the runtime), OR
   - Rebuild it deterministically from the runtime view on every `on_fill` (replace the lot replay with a snapshot of the runtime positions).
3. Add a debug invariant: at end of every `decide()`, assert `auto_fill_state.yes_qty()` ≈ `inventory.yes_qty` (within accounting epsilon). Fail loud in tests, log loudly in prod.

## Finding 3 — Single-leg stranded markets never produce a `Merge` intent

**Severity:** Medium. Primary recovery path for stranded inventory bypasses the merge gate entirely.

`runtime/mod.rs:1180-1240` `inventory_merge_intent`:

```rust
if positions.len() != 2 {
    return None;
}
```

If a market has only one leg (the stranded case), this returns None and the runtime never emits `RuntimeCommand::Merge`. The only escape is `RescueAction::BuyOppositeForMerge` from the rescue engine, which manufactures the missing leg via an IOC against the opposite ask. If the opposite ask is wide / unfavorable / the rescue cooldown is active / `RescueConfig.allow_sell_fallback = false` and `require_no_guaranteed_loss = true` blocks both arms, the inventory is parked indefinitely.

There is no counter that says "this market has been single-leg-stranded for N minutes, surface to operator." The metrics gauge (`metrics.rs:286-292` `stranded_yes_qty`/`stranded_no_qty`) is operational data, not an actionable alert seam.

**Recommendation:**

1. Add a `markets_with_stranded_inventory_first_seen_ms: HashMap<MarketId, EpochMillis>` to `Runtime`, parallel to `markets_with_drift_first_seen_ms` (which already exists at `runtime/mod.rs:85`). Populate it when `inventory_merge_intent` returns None *and* the market has any non-zero positions.
2. After a configurable `stranded_alert_threshold_ms`, emit a structured `EventCategory::Risk` event so it lands in dashboards. Don't act on it — just surface it.
3. Document the rescue-engine config caveats (the AND of `require_no_guaranteed_loss` and `allow_sell_fallback=false` makes rescue impossible in some price configurations) in a comment on `RescueConfig` so operators don't accidentally configure themselves into a non-recoverable state.

## Finding 4 — `IntentKind::Close` exists but five consumers still match strings

**Severity:** Medium. Cosmetic for the obvious sites, but each one is a place where a refactor could re-trap close intents.

`core/types.rs:208-230` introduces `IntentKind::{Entry, Close}` with a long comment explaining why the previous five `tag.starts_with("mm-hedge-rescue")` checks were promoted. But the substring checks were not all removed:

| Site | What it does | Should be |
|---|---|---|
| `runtime/mod.rs:3501` | `is_some_and(\|tag\| tag.starts_with("mm-hedge-rescue"))` | `intent.kind == IntentKind::Close` |
| `runtime/mod.rs:3540` | same pattern | same |
| `runtime/attribution.rs:126` | classifies attribution bucket | check `IntentKind` (and fall back to substring only if Entry) |
| `paper/report.rs:858` | classifies fill in report | same |
| `runtime/mod.rs:2655` `is_paired_entry_intent` | matches `mm-paired-bid` / `:PairedEntry` substring | should match on `IntentKind::Entry` plus a `category` field — see Finding 1 |

The `MmQuoteKind::from_quote_level_tag` parser (`core/types.rs:399`) is a separate concern: it's used at the *report seam* to derive a typed kind from a tag for analytics, after the intent has executed. It's fine to keep it as a substring parser there — but it should not be the source of truth at any decision boundary.

**Recommendation:**

1. Replace the five sites above with `intent.kind == IntentKind::Close`.
2. For `is_paired_entry_intent`, decide whether the "is paired entry" predicate belongs on `IntentKind` (split it into `Entry { paired: bool }` or add a third variant) or as a separate `category: IntentCategory` field. Either is fine; the current substring is brittle.

## Finding 5 — Two distinct rescue triggers, no clear ownership

**Severity:** Medium. Risk of double-fire, harder to reason about which path fires when.

There are two rescue trigger paths:

1. **Snapshot-driven**: `paired_mm/engine.rs:202-211` inside `decide()`. `derive_tick_rescue_inputs` builds rescue inputs from `(snapshot, inventory, fair_value)`. Fires every decide tick.
2. **Fill-driven**: `paired_mm/engine.rs:169-181` `on_fill` calls `AutoFillState::on_fill` which calls `evaluate_snapshot`. Fires after every per-leg fill.

Both call `choose_rescue` (`pairing/rescue_engine.rs:61`) with similar but not identical inputs:

- `decide()` path uses `inventory.yes_qty / no_qty` (runtime view).
- `on_fill()` path uses `AutoFillState.yes_qty() / no_qty()` (local view, see Finding 2).

The decisions are routed differently:
- `decide()` returns `PairedMmDecision { rescue, ... }`.
- `on_fill()` returns `AutoFillDecision { suggestion: AutoFillSuggestion::Rescue { decision } }`.

Whoever consumes both must coordinate — but the consumer is the strategy adapter (`strategies/paired_mm.rs`), and a quick read suggests both can produce intents in the same tick.

**Recommendation:**

1. Pick one trigger path. The fill-driven path is what reflects the real position; the snapshot-driven path is only useful when a fill event was missed (WS reconnect, dedup). Keep snapshot as a fallback that *only* fires if `last_fill_ms` is older than some threshold.
2. Or, consolidate by making the `decide()` path internally consult `AutoFillState` (which lives on the engine) and not re-derive from snapshot. That way there's one rescue brain.

## Finding 6 — `runtime/mod.rs` (3,579 lines) and `runtime/runner.rs` (3,641 lines) are too large to safely refactor

**Severity:** Process. Not a bug, but it is the biggest predictor of *future* bugs.

These two files are the primary orchestrators. They have too much surface for a single reader to hold at once, which means impact analysis on any change in this area is unreliable. A few seams that scream for extraction:

- Merge orchestration (`mod.rs:1180-1240` plus surrounding pressure-detection helpers) → `runtime/merge_gate.rs`.
- Pair-atomicity logic (`mod.rs:1991-2033` + `mod.rs:2601-2661`) → `runtime/pair_atomicity.rs`.
- Drift detection (`mod.rs:80-92` + the `markets_with_unresolved_drift` machinery) → `runtime/drift.rs`.
- Order acknowledgement / fill posting (`mod.rs:2664+` `accept_intent` and friends) → `runtime/order_lifecycle.rs`.

None of these is urgent, but the next major refactor (e.g. the changes implied by Findings 1–5) will be much safer if these are extracted first.

## Finding 7 — `choose_convex_overlay` uses a 19-element tuple to swap legs

**Severity:** Low. Pure code-smell, but it makes the late-convex code path the easiest to break.

`paired_mm/engine.rs:400-466`: the function returns a 19-element tuple from a single `if/else` in order to swap "favorite" and "tail" leg references. Adding a new field requires editing the tuple in three places (struct, both branches), which is exactly the change a future engineer is likely to get wrong.

**Recommendation:** introduce a small private struct, e.g.

```rust
struct ConvexLeg<'a> {
    tag: &'static str,
    instrument_id: InstrumentId,
    quote: &'a QuoteSnapshot,
    win_prob: f64,
    current_qty: f64,
    open_qty: f64,
    open_notional: f64,
    open_count: usize,
    avg_cost: f64,
}
```

Both branches return `(ConvexLeg, ConvexLeg)`. Field access is positional-free.

## Finding 8 — `RescueConfig::allow_sell_fallback` and `require_no_guaranteed_loss` interaction

**Severity:** Low (configuration), but operationally important.

`pairing/rescue_engine.rs:80-92`:

- If `require_no_guaranteed_loss = true` and `avg_cost + opposite_ask > 1.0 - edge`, the merge-rescue arm is rejected.
- If `allow_sell_fallback = false`, the sell arm is unavailable.

So a market where:
- Avg cost on the stranded leg is high (entered late at e.g. 0.65)
- Opposite ask is also high (e.g. 0.40)
- Edge config is non-trivial (e.g. 50bps = 0.005)

`0.65 + 0.40 = 1.05 > 1.0 - 0.005`, merge-rescue rejected. If sell fallback is off, the entire rescue path returns `Hold`, and inventory parks until either (a) the opposite ask drops, (b) fair value moves, (c) human intervention.

**Recommendation:**

- Document this clearly in `RescueConfig` doc comments.
- Consider a "deadline pressure" mode that flips `allow_sell_fallback` to true automatically when `time_remaining_ms < N`.

## Finding 10 — `aws_config::load_from_env` is deprecated

`infra/s3_parquet.rs` (and similar) still calls `aws_config::load_from_env`. This will silently change default behavior in future AWS SDK versions (`behavior-version-latest`). Migrate to `aws_config::defaults(BehaviorVersion::latest()).load().await`.

Low urgency, but worth landing alongside the next AWS SDK bump.
